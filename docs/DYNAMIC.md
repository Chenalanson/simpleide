# 动态监测（watchpoint）教程

动态监测用 GDB 的 watchpoint 观察变量或内存地址：目标跑到写入（或读取）这些位置时，GDB 会让程序暂停，应用记录这次变化的时间、旧值、新值、停止位置和调用栈。

它和 **静态检测** 的区别：

| | 静态检测 | 动态监测 |
| --- | --- | --- |
| 是否需要调试 | 不需要 | 需要调试会话 |
| 检查对象 | 源码中的数组下标、字符串函数、malloc/free | 运行中的变量、结构体成员、内存地址 |
| 发现方式 | 规则扫描 | 目标访问被观察位置时暂停 |
| 能否看到调用栈 | 不能 | 能记录当前停止位置和 GDB 调用栈 |

动态监测不是完整的数据流追踪器，也不是 ETM 指令追踪。它只在 **watchpoint 命中时** 记录一次事件；高频变量、优化后被内联的变量和被编译器优化掉的变量可能看不到，或者看到的调用栈不完整。

---

## 能追踪某个变量的变化吗？

**可以。** 只要变量在目标上有稳定地址，并且当前调试会话能解析它，就可以用 watchpoint 追踪它的读取或写入：

- 全局变量 / 静态变量：`g_state`、`uwTick`
- 结构体成员：`motor.pwm`、`sensor.value`
- 数组元素：`buffer[3]`、`rx_buf[head]`
- 指针解引用 / 固定地址：`*ptr`、`*(uint32_t*)0x20000000`
- 局部变量：在变量所在函数暂停后添加；建议使用 `-O0` / `-Og`，变量被优化到寄存器时可能无法建立 watchpoint

每次命中都会暂停目标，并记录本机时间、旧值 → 新值、停止位置和调用栈。因此它不仅回答“值什么时候变了”，还能回答“是哪一行写的、从哪个调用链写进来的”。

三种追踪方式：

| 方式 | 关注点 | 典型用途 |
| --- | --- | --- |
| 写入 `watch` | 值被写入时暂停 | 找谁改了状态、标志、计数器 |
| 读取 `rwatch` | 值被读取时暂停 | 找哪些代码在消费这个变量 |
| 读写 `awatch` | 读或写都暂停 | 同时观察读写访问 |

## 它能做什么

| 场景 | 可以设置 | 能看到的记录 |
| --- | --- | --- |
| 状态机卡住 / 状态被意外改写 | `watch state` | 每次写入的时间、旧值 → 新值、写入行和调用栈 |
| 标志位被别处清零 | `watch error_flag` | 是哪条代码路径把标志改掉 |
| 计数器 / 时钟 tick | `watch uwTick` | 每次递增的先后顺序和调用者 |
| 结构体字段异常 | `watch motor.pwm` | 精确到字段的写入位置 |
| 数组元素被覆盖 | `watch buffer[3]` | 覆盖发生的源码行和调用链 |
| 谁在读某个变量 | `rwatch flag` | 读取位置和调用栈 |
| 固定寄存器 / 内存地址 | `awatch *(uint32_t*)0x20000000` | 读/写访问（受目标和探针支持限制） |
| 调试重启后继续观察 | 勾选“调试时自动启动动态监测” | 自动重新挂载已保存的表达式 |

这些记录适合定位“变量被谁改掉”“某个状态从哪条路径进入”“某个读取发生在哪个任务/中断里”这类问题。

## 它不能做什么

- **不是持续采样或曲线记录**：每次命中都会暂停 CPU，不能像逻辑分析仪那样连续记录高频变量。
- **不是完整的数据流 / ETM 追踪**：只记录 watchpoint 命中的瞬间，不记录每条指令或所有历史写入。
- **硬件比较器有限**：Cortex-M 通常只有 2–4 个；数量不够时 GDB 可能退化为软件 watchpoint，速度明显变慢。
- **DMA 或其他总线主控的写入不一定触发**：CPU watchpoint 主要观察处理器访问，DMA 直接写内存时不保证命中。
- **优化会影响结果**：变量被放进寄存器、被内联或消除时，可能无法建立 watchpoint，调用栈也可能不完整。
- **局部变量有时效性**：离开作用域后地址失效，通常要在函数内部暂停时添加。
- **时间戳是本机时间**：用于判断先后顺序，不是 MCU 周期或精确触发时刻。
- **每个监测点最多保留 200 条记录**，超出后丢弃最旧的记录。
- **不能替代静态检测 / ASAN / Valgrind**：静态扫描找源码模式，动态监测只回答运行时访问问题。

## 1. 准备工作

1. 工程能正常构建，并且编译时带调试信息（GCC/Clang 通常使用 `-g`；优化等级建议先用 `-O0` 或 `-Og`）。
2. 已经配置好调试：
   - **调试程序**：ELF / AXF / EXE 产物
   - **gdb 路径**：`arm-none-eabi-gdb`（ARM）或主机 gdb
   - ARM 目标还需要能工作的 OpenOCD 或 pyOCD 配置
3. 目标板已连接，调试探针可用。

设置入口：

- 调试程序和 gdb 路径：**配置 → 调试**
- OpenOCD / pyOCD：**工程信息 → 烧录配置 → 编辑**

调试程序为空时，应用会按修改时间在 `build/`、`Debug/`、`Release/`、`out/` 和工程根目录查找最新的 ELF / AXF / EXE。

---

## 2. 启动调试

按 `F5`，或点右侧 **调试**。

首次启动会停在 `main`，方便设置断点和 watchpoint。调试会话启动后：

- 右侧调试侧栏可用
- 底部输出面板切到 **调试输出**
- 编辑器右上角出现调试控制浮层

添加 watchpoint 前，目标必须是 **暂停** 状态。目标正在运行时，动态监测页会提示先按 `F5` 暂停。

---

## 3. 打开动态监测

点右侧 **检测**，在“非法检测”窗口切到 **动态监测**。

没有调试会话时，页面会显示：

```text
动态监测需要调试会话
启动调试后，在这里输入变量名或地址表达式即可添加硬件 watchpoint。
```

如果有会话，页面显示输入框、监测点类型下拉框和已保存的 watchpoint 列表。

### 调试时自动启动

动态监测页有一个复选框：

```text
[ ] 调试时自动启动动态监测
```

勾选后，下次启动调试会话时会自动：

1. 打开“非法检测 → 动态监测”
2. 重新启用已保存的 watchpoint 表达式

这个开关会保存到全局设置，下次启动应用仍然生效。

如果关闭自动启动，已保存的 watchpoint 不会自动重新挂到新的调试会话；可以在页面里点 **重新启用监测点** 手动恢复。

---

## 4. 添加 watchpoint

在表达式输入框里输入变量名、结构体成员或地址表达式，例如：

```text
uwTick
counter
state.active
buffer[3]
*(uint32_t*)0x20000000
```

选择监测类型：

| 类型 | GDB 命令 | 触发条件 |
| --- | --- | --- |
| 写入 | `watch` | 值被写入时暂停 |
| 读取 | `rwatch` | 值被读取时暂停 |
| 读写 | `awatch` | 读或写都会暂停 |

点 **添加**。

Cortex-M 通常只有 2–4 个硬件比较器。GDB 会优先使用硬件 watchpoint；数量不够时可能退化为软件 watchpoint，速度会明显变慢。列表里标有 **软件** 的条目就是软件 watchpoint。

目标运行时不能添加。先暂停，再添加；如果表达式暂时无法求值（例如变量还没进入作用域），GDB 会返回错误，检查变量名、作用域和优化等级。

---

## 5. 查看变化记录

每次命中后，watchpoint 行会显示：

- 编号和监测类型
- 表达式
- 命中次数
- 最近一次旧值 → 新值

如果产生了历史，下面会出现可折叠的：

```text
变化记录 (N)
```

展开后，每条记录包含：

```text
21:42:18.317   0 -> 1   main () at src/main.c:42
```

- **时间**：本机本地时间，精确到毫秒
- **旧值 → 新值**：GDB 报告的 `Old value` / `New value`
- **位置**：GDB 命中后停止的函数和源码行，通常就是实际执行写入/读取的位置

如果 GDB 返回了调用栈，记录下方还会有 **调用栈** 折叠项，例如：

```text
#0  HAL_IncTick () at Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal.c:...
#1  SysTick_Handler () at Core/Src/stm32f1xx_it.c:...
#2  <signal handler called>
```

它回答两个问题：

- **谁改变了它**：看“位置”里的当前函数和源码行
- **谁调用了它**：展开“调用栈”，从 `#0` 往下看调用链

注意：这里的“位置”和调用栈来自 watchpoint 命中时的 GDB 现场，不是编译器插桩的完整写入日志。优化等级较高时，函数可能被内联、变量可能被放进寄存器，位置和栈会不完整。

### 清空记录

- **清空记录**：保留 watchpoint，只清空历史
- **全部删除**：删除所有 watchpoint 和历史

历史最多保留 200 条/每个监测点，超出后丢弃最旧的记录。

## 6. 一个完整例子

观察 `uwTick` 被谁递增：

1. 构建并启动调试
2. 暂停在 `main`
3. 打开 **检测 → 动态监测**
4. 输入 `uwTick`，类型选 **写入**
5. 点 **添加**
6. 按 `F5` 继续运行
7. 等 SysTick 中断触发

命中后目标自动暂停，列表出现：

```text
#2  写入  uwTick  命中 1 次  4294967294 -> 4294967295
变化记录 (1)
  21:42:18.317  4294967294 -> 4294967295  HAL_IncTick () at .../stm32f1xx_hal.c:...
  调用栈
    #0 HAL_IncTick () at .../stm32f1xx_hal.c:...
    #1 SysTick_Handler () at .../stm32f1xx_it.c:...
```

继续运行会继续记录新的变化；每次命中都会追加一条带时间戳的记录。

### 例 2：追踪一个被意外改写的标志

```c
volatile uint8_t g_ready;
volatile uint32_t g_state;

void sensor_task(void) {
    g_ready = 1;      /* 正常置位 */
}

void fault_handler(void) {
    g_ready = 0;      /* 怀疑这里误清零 */
}
```

1. 使用 `-O0` 或 `-Og` 编译，启动调试并停在 `main`
2. 在 **非法检测 → 动态监测** 输入 `g_ready`，类型选 **写入**，点 **添加**
3. 按 `F5` 继续运行；`sensor_task` 和 `fault_handler` 每次写这个变量都会让目标暂停
4. 展开 **变化记录**，查看 `0 -> 1` / `1 -> 0` 的时间、源码位置和调用栈

如果记录显示 `1 -> 0` 停在 `fault_handler`，就能确认清零来自哪条代码路径；这比只设置断点更容易发现“某个值在什么时候被别处改掉”。

---

## 7. 会话生命周期

- 启动调试：如果开启了 **调试时自动启动动态监测**，会重新挂载已保存的 watchpoint
- 停止调试：watchpoint 表达式和历史保留，但 GDB 编号失效；再次启动后需要自动或手动重新启用
- 切换工程：清空当前工程的 watchpoint 和历史
- **重新启用监测点**：用当前暂停目标重新发送所有已保存表达式的 watch 命令
- **全部删除**：同时删除表达式、编号和历史

---

## 8. 和调用栈有关的限制

GDB 的 `bt` 只能看到当前线程/当前栈帧能解析出的调用链：

- 优化后函数内联，调用栈可能少几层
- 中断处理函数和 RTOS 任务切换可能让栈看起来不连续
- 变量被优化到寄存器时，watchpoint 可能无法建立或只在特定时刻有效
- 软件 watchpoint 通过单步执行实现，命中位置和速度都不如硬件 watchpoint
- 高频写入（例如 1 kHz 以上的计数器）会让目标频繁暂停，建议只在短时间窗口内观察

如果只需要检查数组越界、危险字符串函数或重复释放，优先使用 **静态检测**，不需要启动调试。

## 9. 常见问题

### 提示 `No symbol "xxx" in current context`

- 当前暂停位置看不到该变量：先在作用域内设置断点
- 编译没有带 `-g`，或优化把变量优化掉了
- 变量名拼写、结构体成员路径不正确

### `Cannot insert hardware watchpoint`

硬件比较器用完了。删除不需要的 watchpoint，或接受 GDB 的软件 watchpoint（会更慢）。

### 添加后没有命中

- 目标没有真正访问该位置
- 变量被优化成寄存器或常量
- watchpoint 设置在错误的地址/表达式上
- 目标一直在运行，没有触发对应代码路径

### 命中后没有调用栈

`bt` 输出可能被目标继续运行打断，或者当前栈无法解析。先确认目标停在 watchpoint 命中现场，再展开“调用栈”；必要时降低优化等级重新编译。

### 时间戳看起来不对

时间来自本机 Windows 本地时间，不是目标 MCU 的时钟。它表示应用收到并解析 GDB 命中事件的时间，适合判断先后顺序，不适合做精确的周期测量。
