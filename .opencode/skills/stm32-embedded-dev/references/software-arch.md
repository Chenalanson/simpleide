## 1. 三层次判定顺序（先范式、再调度、后模式）

| 顺序 | 维度 | 回答的问题 | 产出位置 |
|---|---|---|---|
| ① | 执行范式 | 程序总体以什么形态运行（主循环扫描 / 事件分发 / 多任务线程） | framework.md 2.1 |
| ② | 调度模式 | 选定范式下任务按什么机制被安排执行（时间片/优先级/事件队列） | framework.md 2.2 + 任务表 |
| ③ | 设计模式 | 代码内部用什么手法组织（状态机、回调注册、句柄单例…） | framework.md 2.3 |

判定纪律：不得跳过范式直接写调度代码；范式结论与调度机制必须相互匹配（前后台不配 RTOS 阻塞队列，RTOS 范式不回退裸机轮询语义）；设计模式为实现层选择，不替代范式/调度结论。

## 2. 执行范式选型

| 范式 | 结构特征 | 适用场景 | 不适用/代价 |
|---|---|---|---|
| **前后台（foreground/background，默认）** | 前台主循环顺序扫描各任务；后台 ISR 响应即时事件；无内核、无独立任务栈 | 资源受限 MCU；任务多为短周期采集、UI、保护逻辑；无硬实时抢占要求 | 无优先级抢占，长任务阻塞全体；任务间天然无栈隔离 |
| 事件驱动 | 事件标志/事件队列 + 分发表，事件到达后调对应处理函数；主循环可只做分发 | 输入密集（按键、通信帧、状态跳变）；逻辑由外部事件触发而非固定节拍 | 固定周期密集采样需另配周期任务兜底；事件丢失风险要保护 |
| 抢占式多任务（RTOS） | 多个任务线程 + 独立栈；内核按优先级切换；支持队列/信号量 | 并发阻塞 IO、明确优先级、任务可阻塞等待、团队维护能力具备 | RAM/Flash 开销大；需管理优先级翻转、栈水位与临界区 |

选型判据：

1. 是否存在「必须即时抢占其他任务」的事件（急停、过流锁存）？有 → 抢占式多任务，或在前后台下用高优先级硬件中断承担该响应。
2. 是否大量阻塞等待（协议交互、屏幕刷新、等待器件就绪）？是 → 事件驱动或 RTOS，避免主循环空转。
3. RAM 是否紧张（<16 KB 可用）且任务数 ≤8？是 → 前后台。
4. 结论写入 framework.md 2.1，附 1~3 条选型理由（对照本表适用/代价列）。

## 3. 调度模式

### 3.1 范式 × 调度对照

| 执行范式 | 可选调度机制 | 默认建议 |
|---|---|---|
| 前后台 | ①非抢占时间片轮询 ②纯状态机连续扫描 ③硬件定时器节拍置标志 | ①为主、②为辅：时间片触发周期任务，循环线程扫描状态机 |
| 事件驱动 | 事件队列/标志位分发 + 周期任务兜底 | 环形事件缓冲 + 主循环分发表 |
| 抢占式多任务 | 优先级抢占调度 + 时间片轮转；周期节拍用 `vTaskDelayUntil` | 高优先级安全任务、低优先级通信/UI（细节见 `code-rules.md` 第 6 节） |

### 3.2 默认：前后台 + 非抢占时间片轮询

#### 3.2.1 双线程结构

| 线程 | 位置 | 职责 | 特点 |
|---|---|---|---|
| `app_sched_thread()` | 主循环 | 检查各任务时间变量到点后调用对应周期任务 | 时间片触发；注册顺序等效静态优先级 |
| `app_loop_thread()` | 主循环 | 连续调用状态机任务，每次只推进一个状态 | 瞬时判断，不挂固定间隔；解决异步等待 |

命名固定：APP 对外只有 `app_init` / `app_sched_thread` / `app_loop_thread`；调度器内部函数名（如 `task_create` / `task_time_sched`）与框架自带 API 均为参考实现，落地时按工程实际适配，不新增同义入口。

时基：SysTick 1ms 中断 `sys_tick_ms++`（`volatile`）；中断内只做计数与定时器递减，不跑业务。

#### 3.2.2 调度器最小实现（参照）

> `task_create` / `task_time_sched` 为参考实现命名，需按工程调度器适配；APP 侧仍固定 `app_init` / `app_sched_thread` / `app_loop_thread`。

```c
typedef struct {
    void (*task_func)(void);
    uint32_t interval;      /* 周期 ms，0 表示仅循环线程调用 */
    uint32_t last_run;
} Task;

static Task s_tasks[MAX_TASK_NUM];

void task_create(uint8_t id, void (*fn)(void), uint32_t interval)
{
    s_tasks[id].task_func = fn;
    s_tasks[id].interval  = interval;
    s_tasks[id].last_run  = 0;
}

void task_time_sched(void)
{
    for (uint8_t i = 0; i < MAX_TASK_NUM; i++) {
        if (s_tasks[i].task_func == NULL) continue;
        if (sys_tick_ms - s_tasks[i].last_run >= s_tasks[i].interval) {
            s_tasks[i].task_func();
            s_tasks[i].last_run = sys_tick_ms;
        }
    }
}
```

#### 3.2.3 标志位替代方案（无注册表时）

SysTick 中按间隔置标志（`flag_led1=1` 等）；主循环检测标志执行后清零。优点极简；缺点任务多时代码分散，任务数 ≥5 时优先注册表方案。

### 3.3 任务时间变量三触发类型

| 类型 | 触发方式 | 变量行为 | 典型任务 |
|---|---|---|---|
| 周期性 | 到点执行后立即重新赋值重载值 | 每次执行后 `timer = period` | 周期采样、LED 闪烁、定期上报 |
| 一次性 | 事件发生后赋值启动，完成后不再自动重载 | 执行后清零，等待下次事件赋值 | 单次刷新屏幕、按键触发一次配置读取 |
| 条件性 | 满足条件才赋值触发（数据就绪、故障状态变化） | 条件成立时置位/赋值，执行后清除 | 解帧任务、保护动作触发 |

划分规则：状态机判断类任务（菜单扫描、协议解析状态推进）放 `app_loop_thread` 连续执行；定周期采集/上报放 `app_sched_thread` 时间触发。禁止把需要瞬时响应的状态机塞进最小 1ms 的间隔轮询。

### 3.4 RTOS 抢占调度衔接

范式选定抢占式多任务时：任务机制表（`vTaskDelayUntil`、任务通知、队列、互斥量、事件组）与约束 RT1–RT5 查 `code-rules.md` 第 6 节；本文件第 6 节共享数据规则同时适用；framework.md 2.2 任务表替换为「任务名｜优先级｜周期/触发｜栈大小｜阻塞点」。

## 4. 设计模式选用

### 4.1 状态机（最常用，默认用于异步流程）

**核心手法：异步拆解阻塞流程。** 用 `switch-case` + 状态变量替代阻塞等待：发送态 → 等待完成态 → 解析态，每次调度只走一步，避免 `while(等待)` 阻塞调度器。

```c
void dev_uart_task(void)
{
    switch (s_state) {
    case ST_IDLE:
        dev_send_cmd(CMD_MEASURE);
        s_state = ST_WAIT;
        break;
    case ST_WAIT:
        if (dev_parse_response() == PARSE_OK) {
            s_state = ST_IDLE;          /* 解析完成回到空闲，等待下一周期 */
        }
        break;
    default:
        s_state = ST_IDLE;
        break;
    }
}
```

状态表要素：

| 要素 | 说明 |
|---|---|
| 状态枚举 | `ST_IDLE / ST_WAIT_TX / ST_WAIT_RX / ST_PARSE / ST_ERR` |
| 迁移条件 | 事件标志、超时、数据就绪、错误码 |
| 每个状态动作 | 单次执行完成一个小动作，无长延时 |
| 错误态 | 超时/校验失败迁移到错误态，带重试计数与上报 |
| 完全体组合 | 状态枚举 + 事件标志 + 状态迁移表（事件×状态） |

注意：状态变量对 ISR/主循环共享时 `volatile`；多字节上下文访问期间短临界保护；状态迁移可经 MID 日志输出便于定位卡滞。

### 4.2 单例句柄（get_handle）

模块内 `static` 实例 + 获取函数对外暴露，替代 `extern` 全局变量；细节与两种封装方式查 `module-convention.md` 第 4 节。适用：外设句柄、器件实例、配置结构体。

### 4.3 回调注册 / 观察者（设备管理器绑定）

| 方案 | 数据结构 | 适用 |
|---|---|---|
| 回调绑定数组（默认推荐） | `{name, init_fn, write_fn, read_fn}` 定长数组 | 资源紧张、设备数量可枚举；RAM 占用可预测 |
| 静态链表 | 节点指针串联 | 设备数量不可预测的网关类；增删灵活但指针开销大 |

```c
typedef struct {
    const char *name;          /* 语义名，供高级 API 寻址 */
    uint8_t  (*init_fn)(void);
    uint8_t  (*write_fn)(uint8_t reg, const uint8_t *buf, uint16_t len);
    uint8_t  (*read_fn)(uint8_t reg, uint8_t *buf, uint16_t len); /* 不适用传 NULL */
} dev_entry_t;
```

规则：读函数与速率要求冲突（需区分 8/16 位或高速专用路径）时 `read_fn` 允许传 `NULL`；无实际多设备复用需求时可省略设备管理器，不强行引入。

设备管理器分两层 API（与 `architecture.md` 第 2 节、`code-rules.md` 5.6 一致）：

| 层级 | API 原型 | 参数 | 调用者 |
|---|---|---|---|
| 高层（设备名寻址） | `dev_write(name, reg, buf, len)` / `dev_read(name, reg, buf, len)` | `name`=注册名；`reg`=寄存器/命令；`buf/len`=数据；单字节命令可简写 `dev_write(name, reg)` | MID service / APP |
| 低层（总线寻址） | `dev_write_reg(bus, reg, buf, len)` / `dev_read_reg(bus, reg, buf, len)` | `bus`=总线实例/句柄；`reg`=寄存器/命令；`buf/len`=数据 | 设备管理器内部 / 驱动适配层 |

`dev_entry_t.write_fn/read_fn` 是绑定到具体设备后的回调，签名不带 `name`；高层 `dev_write` 先按 `name` 查表命中 `dev_entry_t`，再转调 `write_fn` 或 `dev_write_reg`。

### 4.4 门面 / 解释层高级 API

MID service 层封装业务语义接口（`power_set("SC8701", 8.20f)`）：完成单位换算、量程约束、寻址后再调用高层 `dev_write("SC8701", 0x21, buf, len)`；屏蔽底层寄存器与总线细节。

### 4.5 注册表寻址

设备管理器 `name → 接口表` 统一访问入口；高层按 `name` 寻址，低层按 `bus` 访问；价值：统一命名寻址、屏蔽总线差异、供上层与测试脚本复用。

### 4.6 生产者-消费者环形缓冲

ISR/DMA 生产数据、任务消费解析，无锁协作；缓冲 `volatile`，head/tail 取模回绕；适用 UART/DMA 接收链路。

### 4.7 设计模式选用清单（framework.md 2.3 节直接照填）

| 模式 | 本工程落点 | 解决的问题 |
|---|---|---|
| 状态机 | 协议器件任务、UI 菜单、保护逻辑 | 异步拆解流程，消除阻塞 |
| 单例句柄（get_handle） | 模块私有实例对外暴露 | 替代 extern 全局变量，降低耦合 |
| 回调注册/观察者 | 设备管理器绑定、按键事件回调 | 解耦触发源与处理函数 |
| 门面/解释层高级 API | MID service 层 | 业务语义封装底层寄存器/总线操作 |
| 注册表寻址 | 设备管理器 name → 接口表 | 统一访问入口 |
| 环形缓冲生产者-消费者 | UART/DMA 接收链路 | ISR 生产、任务消费，无锁协作 |

## 5. 非阻塞设计与延时处理

| 手法 | 适用 | 实现 |
|---|---|---|
| 状态机等待态 | 通信、转换等待（如温变 20ms） | 拆 `ST_WAIT_XXX`，由时间变量到点推进 |
| 软件定时器重载值修改 | 一次性延时/节拍调整 | 直接改写任务时间变量，到点执行回调 |
| 框架定时组件 | 已用调度框架 | 使用框架延时 API，不用裸忙等 |
| `HAL_Delay`/`LL_mDelay` | 仅 `app_init` 器件上电稳定阶段允许 | 主循环/任务/ISR 中禁止长阻塞延时 |

## 6. 共享数据与临界资源

| 场景 | 处理规则 |
|---|---|
| 前后台非抢占模型 | 任务间不互相抢占，数据经模块 get/set 交换；ISR 与主循环共享变量加 `volatile` |
| ISR 写、主循环读 | 环形缓冲 + 索引；单次多字节搬运在短关中断内完成；禁止 ISR 内调用阻塞接口 |
| RTOS 模型 | 队列传递数据副本；互斥量保护共享句柄；`FromISR` API 专用 |
| 寄存器级共享（外设句柄） | 同一外设的多访问点串行化（状态标志/简单互斥），避免时序交错 |
| 临界区 | 短开关中断或互斥量；临界区内无阻塞调用、无打印 |

## 7. 任务划分原则与耗时约束

1. 单一职责：一个任务对应一个功能域（采集、保护、UI、通信、存储）。
2. 耗时预算：单次任务执行远小于最短调度周期；状态机单状态动作控制在毫秒级以内。
3. 阻塞上移：阻塞/等待逻辑拆进状态机；数据生产者（ISR/DMA）与消费者（任务）解耦。
4. 保护类任务（OVP/OCP/OTP）周期短、判断直接；故障动作直接调用安全输出接口。
5. 任务清单（名称/触发类型/周期/状态集/依赖接口）写入 framework.md 2.2 节；范式为 RTOS 时按 3.4 节表结构填写。
