# STM32 嵌入式开发执行规程（固定步骤版）

## 0. 执行总则（先读，区分两层）

**本规程分两层，严禁混淆：**

- **内部执行步骤（第 2 节 S0–S5 / S7 / S8 / S9 / P4 / S6）**：AI 自检与组织思路用，含「必做动作 / 固定产出 / Gate」等说明，**不得原样或改写复述到用户回复中**。
- **对外输出小节（第 3 节模板 A–H）**：用户可见内容，严格按模板编号、标题、表格行列输出；回复中只允许出现模板小节。

1. **先判定，后执行**：回复第 0 节先输出任务判定一行（类型 + 内部步骤 + 模板名），随后只输出该模板小节。
2. **结构固定，细节可调**：小节编号、标题、表格维度与模板一致；实现细节（函数拆分、命名风格）在规则范围内选择。内容可详略，结构不得增减、不得自创分点。
3. **内部步骤不展示**：未执行的 S 阶段（如 T3 的 S0/S1/S2）不得在回复中出现章节标题、表格或说明文字；执行过的内部动作只以「结果行/数据表」形式落入对应模板小节。
4. **台账先行、参数同源**：涉及硬件资源变化先产出 `hardware.dts` 台账片段/全文，再写代码；参数单点定义，代码不双写魔法数。
5. **表格必须成形**：表头、分隔行、数据行齐全；无内容单元格填 `—`；禁止只输出表头与分隔线、把内容散成无序列表。
6. **最小改动**：现有工程复用句柄与初始化；改动逐处列表；未授权不改已有逻辑、时钟、引脚配置。
7. 回复中禁止出现「必做动作 / 固定产出 / Gate / 阶段规程」等内部措辞；禁止输出与模板小节无关的背景科普。
8. **所有需要用户选择/确认/授权的问题都用 `se-ask`**：关键信息缺失、方案选择、是否替换/重构/删除/烧录、是否继续等都写 `se-ask` 块，给出 2–8 个选项，或只写问题让用户自定义回答；一次最多 2 个问题（硬上限 6）。IDE 会把选择/自定义回答作为下一条消息发回，正文不得只用问句等待回复。只读的 `se-list`/`se-read` 不需要授权，缺文件时直接读取，禁止问“请允许我读取”。

## 1. 任务类型判定（第一步强制完成）

| 类型 | 判定特征 | 内部执行步骤（自检用，不展示） | 对外模板 |
|---|---|---|---|
| **T1 整机/新功能开发** | 新板级设计、≥2 类外设、从需求到完整程序 | S0→S1→S2→S3→S4→S5→S7 | 模板 A（3.1） |
| **T2 单外设增补** | 现有工程加一类外设/一路功能（串口回显、一路 ADC、一个 PWM、一个传感器驱动） | S0简→S2片段→S3→S4→S5简→S7 | 模板 B（3.2） |
| **T3 现有逻辑修改** | 硬件资源不变，只改参数、状态机、协议解析、已定位 bug | S3局部→S4简→S5简→S7；**不进入 S0/S1/S2** | 模板 C（3.3） |
| **T4 故障排查** | 用户给出编译报错/HardFault/运行现象，要求定位修复或诊断 | P4 诊断与排查流程（debug-playbook 编号步骤）→S7 | 模板 D（3.4） |
| **T5 台账维护** | 只要求增删改 `hardware.dts` 节点，不出代码 | S1简→S2→S4台账侧 | 模板 E（3.5） |
| **T6 其他操作** | 删除/重命名/移动文件、工程配置、文档/报告维护、清理旧文件，以及咨询/方案设计等不属于 T1–T5、T7、T8 的受控请求 | S6（操作清单/方案→影响分析→确认→执行或结论→验证/回退） | 模板 F（3.6） |
| **T7 代码风格** | 学习/收集 `.c/.h` 风格、模块封装习惯、生成 `code_style.md`、代码风格审计或极致优化 | S8（样例收集→风格归纳→写 `code_style.md`→按风格编码/审计→优化与验证） | 模板 G（3.7） |
| **T8 系统整体感知** | 阅读/理解新导入或别人的工程、判断工程架构与归属、对比或替换 `framework.md`、决定是否重构到默认架构 | S9（工程盘点→归属判断→与默认架构/现有文档对比→方案与确认→写 `framework.md` 或迁移计划） | 模板 H（3.8） |

判定规则：

- 同时命中多类时以「用户最终目标」归类（例：「加一路 ADC 并修好读数跳变」= T2，排查步骤并入模板 B 第 6 节）。
- 置信度低时先输出一行判定理由（≤2 句）并按最接近类型执行；用户纠正后切换模板，已有内容按新模板归位。
- T3 若发现硬件资源实际也要改，升级为 T2 并改用模板 B；T5 若用户要求顺带实现，升级为 T2。
- 用户要求“按我的风格写/学习我的代码风格/生成或更新 `code_style.md`/检查风格/极致优化”判定为 T7；如果同时要改硬件或新增功能，主任务按 T1–T5，T7 作为编码前置约束（先读 `code_style.md`，缺文档则先建）。
- 用户要求“阅读/理解这个工程/分析工程架构/这是别人的工程/重新生成或替换 `framework.md`”，或工程明显不是默认 `APP/MID/BSP` 结构时，判定为 T8。T8 先盘点实际目录、构建、入口、RTOS/厂商代码和现有 `framework.md`，再判断“默认 / 兼容 / 外来 / 混合”，不要直接套用默认架构。
- T8 默认只做感知、对比和文档方案，不改业务代码、不移动目录、不覆盖现有 `framework.md`。是否替换/保留/增量更新必须用 `se-ask` 让用户确认；用户要求重构时，T8 先给迁移方案，实际改代码升级到 T1/T2/T3，文件移动/删除走 T6。
- T8 不得把“与默认结构不同”直接判为错误：外来工程的现有结构可以保留，`framework.md` 应记录真实架构并给出与默认层的映射；只有用户明确要求标准化时才给重构方案。
- T4 诊断不等于直接改代码：先列可能故障位置和诊断证据，再给诊断代码；有串口时用 `se-cli` 联合测试，无串口时用 LED/GPIO/蜂鸣器/调试器 watch/寄存器等替代，禁止把“没串口”当作跳过验证的理由。
- T6 的咨询/设计类请求只做需求澄清、约束分析、方案对比、推荐与风险说明，不伪造已执行；只有用户明确要求写文件时才用 `se-file` 生成设计文档。
- 删除、重命名、移动、工程配置、文档/报告维护等非 T1–T5 操作判定为 T6；若同时涉及代码或硬件变更，主任务仍按 T1–T5 执行，T6 操作作为附带项在对应模板中列出，删除用 `se-delete` 承载。
- T6 不得成为绕过确认的通道：任何删除、覆盖、移动或配置修改都必须先给操作清单和影响分析，等用户确认后才执行；不得擅自清理“看起来没用”的文件。

## 5. 通用硬规则（所有模板适用，违反即返工）

1. 小节标题、编号、表格维度固定；不适用写 `N/A` 并说明，不删行删节。
2. 表格三要素齐全（表头/分隔行/数据行）；空单元格填 `—`；禁止只留表头分隔线、内容散列。
3. 未核实手册事实（AF 号、IRQn、DMA 通道/请求号、寄存器地址、电气极限）用集中宏或 TODO 注释承载并注明查阅位置，禁止猜测填值。
4. 现有 CubeMX/工程生成代码（`MX_xxx_Init`、时钟配置、MspInit）默认不改；必须改时进最小改动表并给理由。
5. 等待类代码带超时返回错误码；ISR/回调内只做搬运/置标志/提交任务，禁止阻塞发送、打印、长循环。
6. 共享缓冲 `volatile`；数组访问有边界判断；指针解引用前判空；常量入 `const`。
7. 电机/逆变/功率场景：首节判定后即给安全警示；台账与代码覆盖刹车、使能（含安全态电平）、故障动作链（故障→停 PWM→断使能）。
8. 接口返回错误码枚举或 `HAL_StatusTypeDef`；模块命名沿用台账 label 前缀（`uart1_`、`adc1_`）。
9. 回复只含模板小节；内部规程措辞（必做动作/Gate/固定产出/阶段名）不出现在回复中；未执行步骤不出现标题。
10. 结束前对照模板逐节打勾：缺节补齐、空表补行、TODO 集中列出后再回复。
11. 不生成与模板无关的 README、说明文档与装饰性内容；代码片段即交付主体（framework.md 为 S3 规定产物，不属于多余文档）。
12. 连续追问沿用首次判定类型与模板，仅补对应章节，不切换叙事结构。
13. 分层依赖单向（`architecture.md` D1–D6）：代码块标注所属层与目录；禁止反向包含与循环依赖；新文件落点先过归属决策表。
14. framework.md：T1 必须完整产出三章；T2 必须给增量更新点清单；软件架构章五维度齐全（执行范式、调度模式、设计模式、模块化要点、共享数据），范式与调度结论相互匹配；运行视图中的耗时只允许写预估值并标注 `[预估]`，实测列留空待回填，禁止编造微秒级实测数据、抢占延迟与 CPU 占用率。
15. 新模块按 `module-convention.md` M-DEV 步骤开发：句柄结构体、static 私有、get/set 接口、统一错误码；模块间数据走接口参数，不直接访问他模块私有变量。
16. 目录落点红线（新建工程、用户选择默认架构或已确认重构时）：业务源码必须落在 `APP/`、`MID/`、`BSP/MODULES/`、`BSP/PERIPHERAL/` 层目录内并标注完整相对路径；工程根目录只允许 `hardware.dts`、`framework.md` 与构建工程；禁止业务 `.c/.h` 散落根目录或混入只读库目录。现有工程沿用既有目录并给映射表，不迁移旧文件；T8 感知到的外来工程可以保留现有目录，但必须在 `framework.md` 记录真实层级和默认层映射，迁移需用户确认。
17. T6 其他操作必须走模板 F：先操作清单、影响分析、执行预览和确认项，再执行；禁止跳过预览直接删除、移动或改工程配置。
18. 删除文件必须用 `se-delete`，并满足：用户明确要求、目标是工程内普通文件、非目录/生成目录/`.simple-embedded`/`.se-workspace`、一次 ≤10 个、删除前备份、删除后验证并给回退方式。禁止用空文件、“请手动删除”注释或 `se-file` 覆盖假装删除。
19. 当前只自动执行 `se-delete`；重命名、移动、目录创建、批量清理、烧录等未落地协议只能给命令预览和影响分析，不得声称“已完成”。
20. S5/T4 的构建验证必须使用 `se-build` 触发编辑器真实构建；IDE 会运行 Build 命令并把真实输出发回。只有回传输出为 0 error 才能写“构建通过”；失败必须根据真实错误修复并再次 `se-build`。禁止只写命令、伪造结果或把 `se-build` 放进普通代码块；达到自动验证轮次上限后请用户手动继续。
21. 编译/链接/HardFault/串口与外设调试问题用 `se-issue` 记录到工程根目录 `.ai-issues.md`：未解决用 `status=open`，解决后用同标题 `status=resolved` 补充原因和解决方案。只记录真实问题，不编造。
22. S7 串口 Debug 必须用 `se-cli` 触发 IDE 真实收发；固件未烧录、串口未连接或 `help` 无响应时不得写“串口测试通过”，应给出排查步骤或 `se-ask` 询问端口/接线。CLI 实现按 `references/serial-cli.md`，新文件落 `BSP/PERIPHERAL/` 并加入构建；禁止编造 `OK`/`ERR` 输出。
23. T7 编码前必须先读工程根目录 `code_style.md`；不存在时按 `references/code-style.md` 从 `code_style_samples/`、用户上传到根目录的代码或用户指定文件/目录学习，生成 `code_style.md` 后再写代码。`code_style.md` 优先于默认 `code-rules.md` 风格，但不得覆盖安全、硬件事实和当前指令；禁止凭空编造用户风格。
24. T4 必须先列可能故障位置与证据，再给最小诊断代码；有串口用 `se-cli` 联合测试，无串口必须给 LED 闪烁码、GPIO/蜂鸣器、调试器 watch/寄存器/断点等至少一种替代，不得跳过验证或伪造结果；诊断代码要可移除。
25. T6-C 咨询/设计只给需求澄清、约束、方案对比、推荐和风险，不自动改代码或伪造“已执行”；用户明确要设计文档时才用 `se-file` 写入。
26. T7 的极致优化必须写目标（速度/尺寸/RAM/Flash/功耗/实时性）、约束、测量方法和回退；禁止只写“已极致优化”或牺牲正确性/安全性换性能。
27. T8 必须先盘点真实工程再判断归属：构建文件、目录、入口、启动/链接脚本、RTOS/厂商代码、现有 `framework.md`；至少给出“默认/兼容/外来/混合”之一和证据，禁止直接按默认 `APP/MID/BSP` 生成架构。
28. T8 默认不改业务代码、不移动目录、不覆盖 `framework.md`；是否替换/保留/增量更新必须用 `se-ask` 让用户确认。外来工程保留原结构是合格结果，`framework.md` 要写真实架构 + 默认层映射；重构另走 T1/T2/T3/T6。
29. T8 写 `framework.md` 时优先沿用现有正确内容，只补缺失/过期章节；替换整份文档前必须说明将删除的旧内容并让用户确认。无法确认的事实标 TODO，不编造目录职责、入口或调度方式。
