# STM32 嵌入式开发执行规程（固定步骤版）

## 0. 执行总则

1. **先判定，后执行**：每次回复先按第 1 节判定任务类型并输出「任务判定」一行，再按对应模板输出。
2. **结构固定，细节可调**：小节编号、标题、核对表维度必须与所选模板一致；实现细节（函数拆分、命名风格）在规则范围内选择。内容可详略，结构不得增减、不得自创分点。
3. **阶段顺序不可跳**：S0→S5 顺序执行；每阶段通过完成门（Gate）才进入下一阶段；Gate 未过时先补齐，不提前输出下游内容。
4. **台账先行、参数同源**：涉及硬件资源变化先产出 `hardware.dts` 台账片段/全文，再写代码；参数单点定义，代码不双写魔法数。
5. **表优先于散文**：信息一律入固定表格；不输出与任务模板无关的背景科普。
6. **最小改动**：现有工程复用句柄与初始化；改动逐处列表说明；未授权不改已有逻辑、时钟、引脚配置。

## 1. 任务类型判定（第一步强制完成）

| 类型 | 判定特征（用户原话/现有上下文） | 执行路径 | 输出模板 |
|---|---|---|---|
| **T1 整机/新功能开发** | 新板级设计、≥2 类外设、从需求到完整程序 | S0→S1→S2→S3→S4→S5 | 模板 A（第 3.1 节） |
| **T2 单外设增补** | 现有工程加一类外设/一路功能（串口回显、一路 ADC、一个 PWM、一个传感器驱动） | S0简→S2片段→S3→S4→S5简 | 模板 B（第 3.2 节） |
| **T3 现有逻辑修改** | 硬件资源不变，只改参数、状态机、协议解析、已定位 bug | S3局部→S4简→S5简 | 模板 C（第 3.3 节） |
| **T4 故障排查** | 用户给出编译报错/HardFault/运行现象，要求定位修复 | 排查规程 P4（第 4.4 节） | 模板 D（第 3.4 节） |
| **T5 台账维护** | 只要求增删改 `hardware.dts` 节点，不出代码 | S1简→S2→S4台账侧 | 模板 E（第 3.5 节） |

判定规则：

- 同时命中多类时，以「用户最终目标」归类（例：「加一路 ADC 并修好读数跳变」= T2，T4 步骤并入 S5）。
- 判定置信度低时，先输出一行判定理由（≤2 句）并按最接近类型执行；用户纠正后切换模板，已输出内容按新模板归位。
- T1/T2 涉及的新硬件资源必须出台账；T3/T5 中资源无变化时台账节标注「台账无变更」，不得省略该小节编号。

## 2. 阶段规程 S0–S5（含完成门 Gate）

### S0 上下文收集

| 项 | 内容 |
|---|---|
| 必做动作 | ①列已知项（型号、库类型、系统形式、现有工程、现有台账）②列缺失项 ③默认假设（未指定时：HAL 库、裸机主循环；假设必须显式标注）④列现有可复用资源（句柄、初始化函数、引脚、公共工具函数） |
| 固定产出 | 表 0-1 已知/缺失/假设；表 0-2 复用资源清单（来源文件:对象名） |
| Gate | 关键缺失（芯片型号、库类型）≤2 个可带假设进入；超过则先提问（≤2 问）；复用资源必须指明文件位置，禁止「假设已有」 |

### S1 需求拆解

| 项 | 内容 |
|---|---|
| 必做动作 | 拆成硬件资源表 + 软件需求表；识别隐含需求（不定长串口→DMA+空闲中断；多通道采集→扫描 DMA；电机→PWM+刹车+电流采样）；列冲突预判（引脚/中断/DMA/缓冲预算） |
| 固定产出 | 表 1-1 硬件资源需求（功能→外设类别→路数→关键参数→隐含需求）；表 1-2 软件需求（节拍/状态/协议/数据量/机制）；冲突预判行 |
| Gate | 用户表述的每个功能点都能落到表 1-1 一行；隐含需求已标注；无未解释的资源空缺 |

### S2 台账产出（hardware.dts）

| 项 | 内容 |
|---|---|
| 必做动作 | 按 `references/ledger-schema.md` 落笔：T1 输出完整 `.dts`；T2/T5 输出受影响节点片段；术语与字段语义严格照规范 |
| 固定产出 | 台账代码块（T1 含文件头/全局节点/实例节点/末尾 TODO 汇总块；T2 为节点片段 + 取值来源小表） |
| Gate | ①TODO 集中在汇总块或片段注释，散值不落地猜测整数；②`app-bindings` 引用闭合；③无引脚/中断重复占用；④每个参数有来源（台账原值/手册章节/显式假设） |

### S3 代码实现

| 项 | 内容 |
|---|---|
| 必做动作 | 按 `references/code-rules.md` 分层：板级配置层（对照台账初始化，现有初始化不重写）→ 驱动接口层（模块前缀接口、超时返回、错误码）→ 业务逻辑层（状态机/任务/处理流程）；T3 只产出被修改局部 |
| 固定产出 | 分层代码块，每块标注文件归属（新建 `.c/.h` 或现有文件）与插入位置；最小改动说明表（文件\|位置\|原值\|新值/动作\|原因） |
| Gate | ①参数可溯源台账字段或集中宏定义（`bsp_conf.h` 风格）②现有代码非授权改动 = 0；③错误返回、超时、中断轻量、边界检查落实；④安全故障动作链落地（电机/功率场景） |

### S4 核对

| 项 | 内容 |
|---|---|
| 必做动作 | 固定 8 维台账-代码一致性表（维度见 `references/checklist.md` 第 1 节）；按 `references/checklist.md` 任务适用矩阵选取一/二/三级核对项 |
| 固定产出 | 表 4-1 一致性表（每行状态：一致/待改/缺失/N/A）；表 4-2 待核对事实（项\|依据位置\|状态）；适用的健壮安全项清单 |
| Gate | ①8 行维度逐行有状态值；②「待改/缺失」每行附修复动作；③手册未核实项全部带 TODO 标注；④安全场景无遗漏刹车/使能/故障态项 |

### S5 构建验证与排查

| 项 | 内容 |
|---|---|
| 必做动作 | 给出构建命令与预期检查点；按 `references/debug-playbook.md` 给出本任务相关排查链；列优化提示（RAM/Flash、效率、功耗、可维护性） |
| 固定产出 | 命令块 + 检查点清单；编号排查步骤（≥3 步，按现象对应 playbook 条目）；优化提示条目 |
| Gate | 至少 1 条可执行构建/烧录命令；排查步骤与本任务外设直接相关；T4 任务本阶段即主输出，须含验证步骤 |

## 3. 固定输出模板（小节编号与标题写死，禁止增删改标题）

### 3.1 模板 A — T1 整机/新功能开发

```
0. 任务判定：T1 整机开发（路径 S0→S5）
1. 上下文收集
   1.1 已知/缺失/假设表        1.2 复用资源清单
2. 需求拆解
   2.1 硬件资源需求表          2.2 软件需求表          2.3 冲突预判
3. 台账设计（规划表/时钟规划/分配原则/资源预算）
4. hardware.dts 台账完整内容（文件名 hardware.dts 与保存路径说明）
5. 代码实现
   5.1 板级配置层              5.2 驱动接口层          5.3 业务逻辑层
   5.4 最小改动说明表
6. 核对
   6.1 台账-代码一致性表（8 维）6.2 待核对事实表        6.3 健壮与安全项
7. 构建验证与排查
   7.1 命令与检查点            7.2 排查链（编号步骤）  7.3 优化提示
```

### 3.2 模板 B — T2 单外设增补（小任务默认模板）

```
0. 任务判定：T2 单外设增补（路径 S0简→S2片段→S3→S4→S5简）
1. 复用资源与本次改动清单（复用表 + 新增/修改项表）
2. hardware.dts 台账节点片段
   2.1 dts 片段代码块          2.2 取值来源表（台账字段 ↔ 取值依据）
3. 代码实现
   3.1 板级配置层（沿用则写「沿用不改」+ 理由）
   3.2 驱动接口层（新建文件/接口签名/错误码）
   3.3 业务层调用点（文件:函数:插入位置）
   3.4 最小改动说明表（文件|位置|原值|动作|原因；纯新增写「新增」）
4. 台账-代码一致性表（固定 8 维，不适用写 N/A，禁止整行删除）
5. 待核对事实表（项|依据位置|状态）
6. 构建验证与排查
   6.1 命令与检查点            6.2 排查链（≥3 步编号）
```

### 3.3 模板 C — T3 现有逻辑修改

```
0. 任务判定：T3 逻辑修改（台账无变更时显式标注）
1. 修改对象与现状（文件|函数/位置|当前行为）
2. 修改方案（目标行为|改动点表：文件|位置|原值|新值|原因）
3. 代码修改块（保留必要上下文行 + 新增/修改行；diff 风格标注 +/-）
4. 影响面核对（调用点清单|台账参数是否联动|接口签名兼容性）
5. 验证方法与排查入口（测试输入/预期输出|异常分支处理|排查步骤编号）
```

### 3.4 模板 D — T4 故障排查

```
0. 任务判定：T4（报错类别：编译/链接/HardFault/运行现象子类）
1. 现象复述与已知信息表（报错原文/现象/复现条件/相关文件与寄存器观测值）
2. 定位结论（引用 debug-playbook 编号条目；给出命中原因与排除过程序号）
3. 最小修复方案（改动表 + 代码块；禁止整体重写模块）
4. 验证步骤（操作序列|预期结果|回归检查点）
5. 预防要点（同类错误的规范约束，1~3 条）
```

### 3.5 模板 E — T5 台账维护

```
0. 任务判定：T5 台账维护
1. 变更清单（节点|动作：新增/删除/修改|字段变化）
2. hardware.dts 更新片段（diff 式代码块；整文件重写时给完整块）
3. 一致性复核（引用闭合|占用冲突|TODO 汇总块更新结果）
4. 代码衔接提示（若后续实现，对应 code-rules 章节与待补代码清单）
```

## 5. 通用硬规则（所有模板适用，违反即返工）

1. 每节标题、编号、表格维度固定；不适用项写 `N/A` 并说明，不删除行/节。
2. 未核实的手册事实（AF 号、IRQn、DMA 通道/请求号、寄存器地址、电气极限）用集中宏或 TODO 注释承载，注明查阅位置（RM 章节 / DS 表号 / 原理图位号），禁止猜测填值。
3. 现有 CubeMX/工程生成代码（`MX_xxx_Init`、时钟配置、MspInit）默认不改；必须改时进入最小改动说明表并给理由。
4. 等待类代码带超时参数并返回错误码；ISR 与回调内只做搬运/置标志/提交任务，禁止阻塞发送、打印、长循环。
5. 共享缓冲加 `volatile`；数组访问有边界判断；指针解引用前判空；常量数据入 `const`。
6. 电机/逆变/功率电源场景：首节即给安全警示；台账与代码均覆盖刹车输入、功率使能（含安全态电平）、故障动作链（故障→停 PWM→断使能）。
7. 代码接口返回错误码枚举或 `HAL_StatusTypeDef`；模块命名沿用台账 label 前缀（`uart1_`、`adc1_`）。
8. 结束前对照所选模板逐节打勾：缺节补齐、空表补值、TODO 集中列出后再回复。
9. 不生成与模板无关的 README、文档说明文件与装饰性内容；代码片段即交付主体。
10. 用户连续追问时沿用首次判定类型与模板，仅补对应章节，不切换叙事结构。

## 6. 异常处理

| 情形 | 处理规则 |
|---|---|
| 关键信息缺失且无法合理假设 | S0 Gate 拦截，一次性提出 ≤2 个补全问题（含候选默认值） |
| 资源冲突（引脚复用冲突、DMA/中断不足、缓冲超 RAM） | S1/S2 输出冲突表（双方资源+原因）+ ≥2 个替代方案，不静默选定 |
| 编译报错 | 走模板 D；先按 debug-playbook 报错表分类定位，给最小修改 |
| 用户中途改需求 | 先更新 S1 表与 S2 台账，再改 S3 代码；改动差异记入最小改动说明表 |
| 硬件事实与用户口头描述冲突 | 以 RM/DS/原理图为准列出冲突，标注需人工确认，不单方面按口头值落代码 |
| 越界（PCB 布线、模拟电路设计、芯片选型替代评估） | 明确标注超出本规程范围，只给软件侧配合建议 |
